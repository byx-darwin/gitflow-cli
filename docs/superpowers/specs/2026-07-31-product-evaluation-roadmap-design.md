## 1. 背景与目标

gf（v0.9.0）是一个 Rust 2024 多 crate 工作区项目，定位为**跨平台 Git 工程化工作流编排框架**：统一封装 GitHub / GitLab / GitCode 三大平台差异（底层分别调用 `gh` / `glab` / `gitcode` CLI），配合 Claude Code / Codex / Gemini 等 Agent 平台的 Skills 集合，提供从需求澄清到代码发布的完整 AI 编程工程循环。

本设计文档回答两个问题：

1. **现状如何** —— 从产品负责人、架构师、DevOps 工程师、开源社区运营、终端用户五个角色视角评估项目，识别强项、弱项、机会、威胁。
2. **接下来怎么走** —— 基于评估结论规划 2026 下半年路线图，覆盖三个战略目标（按序）：稳定化并发布 1.0、开源社区增长（含官方网站与 GEO/SEO）、功能扩张。

**边界条件**（已与产品方确认）：

| 条件 | 取值 |
|------|------|
| 战略目标排序 | 稳定 → 增长 → 扩张（三目标全要，按序推进） |
| GitCode 平台策略 | 1.0 前修复至三平台平等可用 |
| 目标用户群 | 中文社区优先（产品描述中文主导） |
| 开发资源 | 单人维护者 + AI 协作（dogfooding 自身工作流） |
| 新增要求 | 官方网站 + GEO（生成式引擎优化）+ SEO（搜索引擎优化） |

## 2. 项目现状事实清单

评估所依据的客观事实（截至 2026-07-31）：

| 维度 | 事实 |
|------|------|
| 版本与规模 | v0.9.0；约 20.8K 行 Rust 代码；6 个 crate（core / github / gitlab / gitcode / e2e-core / e2e-github）+ CLI 应用 |
| 命令面 | 15 个 CLI 命令模块（auth / commit / issue / label / pipeline / pr / release / review / skills / workflow 等） |
| Skills | 26 个，三层结构：编排层（workflow / quality / autoreport-bug）+ 工作流层 + 核心命令层 |
| 测试 | 约 850 个测试函数，分布均衡（core 145 / github 186 / gitlab 153 / gitcode 150 / cli 215）；**e2e crate 近乎空壳**（e2e-core 1 个、e2e-github 0 个） |
| 持续集成 | 6 条 CI 流水线（build / ci / cd / e2e-tests / release / smoke-test）；三平台各有 smoke-test |
| 分发渠道 | crates.io（5 个 crate）+ Homebrew（formula 由 GitHub Actions 机器人自动更新） |
| Agent 生态 | 支持 5 个 Agent 平台（Claude Code / Codex / OpenCode / Gemini / Copilot），Hook 能力矩阵差异化 |
| 工程纪律 | `forbid(unsafe_code)`、pedantic clippy、deny `todo!`/`dbg!`、0 个 TODO/FIXME、core 公开 API 68 项 |
| 文档 | docs/ 下 120 篇、specs/ 下 6 篇；无独立文档站 |
| 维护力量 | 全部提交来自单一作者（bus factor = 1） |
| 已知缺陷 | Issue #90：GitCode 适配器系统性问题（add-label 传错 flag、pr create/list 缺 author 字段、pr view 参数解析错误），GitCode 平台 PR 工作流基本不可用，已开放 10 天 |
| 元数据问题 | Cargo.toml 仍为模板占位符（`Your Name <YourName@yourdomain.com>`、空 `docs.rs` 链接） |
| 历史事故 | 发布流程曾产出未替换模板变量的提交（`release v{{version}}`） |

## 3. 多角色评估

### 3.1 产品负责人视角

| 维度 | 评估 |
|------|------|
| 强项 | 定位精准且差异化：不是又一个 `gh` 封装，而是"AI 编程工程循环编排器"——该生态位目前几乎没有直接竞争者；v0.9.0 距 1.0 一步之遥；发布流水线已自动化（git-cliff + cargo-release + Homebrew 机器人） |
| 弱项 | 无可公开引用的路线图；crates.io 元数据仍是模板占位符，显得不成熟；无采用度数据（不知道谁在用、怎么用）；#90 开放 10 天未响应 |
| 机会 | AI 编程代理生态处于爆发期（Claude Code / Codex / Gemini 均在扩张）；"给 AI 编程上工程纪律"是空白心智；国内 GitCode 生态需要本地化工具链 |
| 威胁 | 平台厂商自行补齐工作流能力（如 GitHub 的 Copilot 代理方向）；skill 生态标准未定型，平台规则变化快 |

### 3.2 架构师视角

| 维度 | 评估 |
|------|------|
| 强项 | Platform trait 抽象干净，依赖单向流动（应用 → 库）；`forbid(unsafe_code)` + pedantic clippy + 禁用 `todo!`/`dbg!`；core 公开 API 规模克制（68 项）；`toon-format` 面向 Agent 消费的 token 优化输出是亮点设计；零 TODO/FIXME |
| 弱项 | **适配器全部通过子进程调用底层 CLI——继承它们的缺陷与版本漂移，Issue #90 正是该架构决策的直接后果**；无针对底层 CLI 版本的契约测试；底层 CLI 最低版本无强制校验；e2e crate 为空壳 |
| 机会 | trait 抽象天然适合暴露为 MCP（模型上下文协议）服务器，成为 Agent 原生接口；契约测试 + 版本矩阵可把"子进程耦合"从负债转为受控边界；插件系统有现成的 trait 接缝 |
| 威胁 | `gh` / `glab` 破坏性变更直接传导；`gitcode` CLI 自身处于 v0.6.x 高波动期 |

### 3.3 DevOps 工程师视角

| 维度 | 评估 |
|------|------|
| 强项 | 6 条 CI 流水线；三平台各有 smoke-test；多语言质量门禁；Homebrew formula 自动更新；nextest + 覆盖率 + pre-commit 齐全 |
| 弱项 | e2e-tests 流水线存在但 e2e crate 无实质内容——流水线在"空转"；发布流程出过模板未替换事故；依赖审计（`make audit`）靠手动触发，无定期巡检；CI 中无平台 CLI 版本锁定 |
| 机会 | 定时 e2e 回归（真实平台凭据）+ 兼容性矩阵徽章；夜间构建跟踪上游 CLI 新版本；SBOM（软件物料清单）与可复现构建提升供应链可信度 |
| 威胁 | 平台凭据的 CI 密钥管理面扩大；GitCode API 不稳定拖累流水线可信度 |

### 3.4 开源社区运营视角

| 维度 | 评估 |
|------|------|
| 强项 | MIT 许可 + Homebrew/cargo 双渠道安装；CLAUDE.md 代理指南本身就是差异化资产（"对 AI 友好的仓库"）；skills 可装入 5 个 Agent 平台，天然多渠道分发；**项目用自身工作流开发自己（dogfooding，即"吃自己的狗粮"），是最有说服力的案例** |
| 弱项 | **bus factor = 1（巴士因子：核心维护者离开即停摆）**；无新手任务管道与贡献者上手路径；模板占位符损害专业感；无公开的 Issue 模板与响应时效承诺；120 篇文档散落仓库，无文档站 |
| 机会 | 中文 AI 开发社区处于内容饥渴期；dogfooding 叙事是天然传播素材；可与 GitCode 平台方联动推广 |
| 威胁 | 单人维护者倦怠；1.0 后社区对稳定性的预期陡增 |

### 3.5 终端用户视角

| 维度 | 评估 |
|------|------|
| 强项 | 平台与 Agent 双自动检测降低上手门槛；JSON / toon / 纯文本三输出模式；shell 补全；skill 提供"流程引导"而非裸命令 |
| 弱项 | 前置依赖重（需预装底层平台 CLI）；**GitCode 上 PR 工作流完全不可用（#90），新用户第一次踩坑即流失**；部分错误直接泄漏底层 CLI 内部信息（如 `unknown flag: --add-label`）；无环境自检工具；文档无统一入口 |
| 机会 | `gitflow doctor` 环境自检命令；5 分钟快速上手；TUI（终端图形界面）提升可探索性 |
| 威胁 | 1.0 前因平台缺陷流失的用户不会回来 |

## 4. 核心诊断：四个结构性矛盾

1. **广度野心 vs 单人产能** —— 3 平台 × 5 Agent × 26 skills 的维护面，只有靠自动化（契约测试 + 定时回归）和 dogfooding 才能可持续。
2. **功能丰富 vs 可靠性不均** —— 功能面已足够宽，但 GitCode 的崩塌证明：1.0 的门槛必须是三平台平等可用，而非功能数量。
3. **Agent 优先创新 vs 双层生态波动** —— 产品价值建立在"平台 CLI + Agent 平台"两层流沙之上，必须用契约测试和兼容性矩阵把边界固化。
4. **中文社区优先 vs crates.io 全球分发** —— 解法是中文主导 + 必要处附英文：产品描述、官网、社区内容中文优先，CLI 帮助与 API 文档保留英文以维持 crates.io 可发现性。

## 5. 路线图战略方案

### 5.1 方案 A：稳定化优先（推荐 ✅）

官网骨架在稳定化末期搭建、**与 1.0 同步上线**；GEO/SEO 内容投入贯穿增长期；扩张期按杠杆率排序选两个方向。

- **优势**：所有流量都被稳定产品承接；1.0 发布事件本身即第一波 SEO/GEO 素材；单人产能下风险最低。
- **代价**：官网搭建压缩在第 7–8 周，骨架必须足够简单（静态站点、核心页面先行）。

### 5.2 方案 B：分发渠道优先

官网与 MCP 服务器提前至第 1–2 月，与稳定化并行。

- **优势**：分发渠道最早成型。
- **代价**：单人 + AI 产能下三线并行（修缺陷 + 建站 + MCP）深度减半；MCP 建在未稳定的 API（GitCode trait 仍在修）上有返工风险；1.0 日期不可控。

### 5.3 方案 C：内容飞轮优先

第 1 月即上线官网与内容矩阵积累受众，同期修缺陷备 1.0。

- **优势**：社区增长从第 1 月启动。
- **代价**：致命缺陷——早期受众会试用产品并踩中 GitCode 缺陷，1.0 前即流失种子用户；违背"稳定 → 增长"的既定排序。

### 5.4 选型理由（选 A）

1. **流量必须由稳定产品承接** —— GEO/SEO 见效有 1–3 个月滞后，官网与 1.0 同步上线，增长期内容正好卡在发布窗口。
2. **单人产能只支持串行主线** —— 每阶段只保留一条主线，深度优于广度。
3. **扩张项按杠杆排序** —— MCP 服务器直接复用现有 Platform trait（架构接缝已确认），投资回报最高；效率报表数据源已存在、成本低；TUI 与插件系统为重资产，放入 2.0。

## 6. 详细路线图

**总览**：

| 阶段 | 时间 | 主题 | 北极星指标 |
|------|------|------|-----------|
| 1. 稳定化 | 第 1–8 周 | 修缺陷 + 固化边界 + 1.0 发布 + 官网骨架 | 三平台 P0/P1 缺陷清零 |

### 6.1 阶段一：稳定化（第 1–8 周）—— "让三平台可信赖，发布 1.0"

#### 第 1–2 周：GitCode 全面修复（关闭 #90）

| 任务 | 细节 |
|------|------|
| 修复 `issue add-label` | GitCode 适配器传入了底层 CLI 不识别的 `--add-label` flag，改为 `gitcode issue` 的正确调用方式 |
| 修复 `pr create/list` 反序列化 | `author` 字段缺失问题，改用 `#[serde(default)]` + `Option` 容错，对齐 GitCode API 实际返回结构 |
| 修复 `pr view` 参数解析 | 修复"接受 1 个参数、收到 2 个"的解析错误 |
| 回归测试 | 测试驱动开发：先写复现测试（红）→ 修复（绿）；#90 的 5 个子问题各对应测试用例 |

**退出标准**：`make smoke-test-gitcode` 全绿；GitCode 平台全部 issue / pr / label 命令可用；#90 关闭。

#### 第 3–4 周：契约测试 + 兼容性矩阵

| 任务 | 细节 |
|------|------|
| 版本护栏 | 强化 `prerequisites.rs`：启动时校验 gh ≥ 2.0 / glab ≥ 1.30 / gitcode ≥ 0.6，不满足时给出友好中文错误与修复指引 |
| 契约测试 | 为每个平台 CLI 的输出格式锁定样本夹具（fixture）；上游变更输出格式时立即报警 |
| 兼容性矩阵 | `docs/compatibility-matrix.md` + 机器可读 JSON（供官网渲染与 AI 抓取） |

**退出标准**：CI 契约测试绿；版本不符时错误信息不再泄漏底层 CLI 内部细节。

#### 第 5–6 周：e2e 实化 + 发布流水线加固

| 任务 | 细节 |
|------|------|
| e2e-core / e2e-github 实化 | 只读实测（`issue list` / `pr list` / `auth status`），CI 使用 GitHub 机器人凭据 |
| 定时回归 | 每周定时运行 e2e；上游 CLI 新版本巡检预警 |
| 发布加固 | 模板变量校验（杜绝 `v{{version}}` 类事故复发）；发布前演练（dry-run）强制清单 |

**退出标准**：e2e-tests 流水线不再空转；1.0 发布演练成功。

#### 第 7–8 周：1.0 准备 + 官网骨架

| 任务 | 细节 |
|------|------|
| 中文主导元数据 | crates.io 五个 crate 的描述改为中文主导（附简短英文）；补全作者、仓库、文档链接 |

| 官网骨架 | Astro 静态站点 + GitHub Pages；中文主导页面：首页 / 文档 / 快速上手 / 兼容性矩阵 / 更新日志；GEO 地基：`llms.txt` + `llms-full.txt` + JSON-LD 结构化数据；站点地图与 robots 文件 |
| 1.0 发布 | 1.0 候选版 → v1.0.0；crates.io + Homebrew 同步；发布宣发文章（掘金 / 知乎 / V2EX） |

**退出标准**：v1.0.0 在 crates.io 与 Homebrew 上线；官网上线；三平台 P0/P1 缺陷清零。

## 7. 官方网站与 GEO/SEO 执行方案

### 7.1 术语表（中文说明）

| 术语 | 中文说明 |
|------|---------|
| GEO（生成式引擎优化） | 让 AI 搜索和 AI 助手在回答"有哪些 Git 工作流工具"时引用、推荐 gf 的优化工作 |
| SEO（搜索引擎优化） | 让百度 / Google / Bing 搜索相关关键词时官网排名靠前 |
| `llms.txt` | 网站根目录下专门给 AI 大模型爬取的全文材料文件，相当于"给 AI 看的网站摘要" |
| JSON-LD 结构化数据 | 嵌在网页里、写给机器看的"结构化名片"，告诉搜索引擎与 AI"这是一个软件，功能是什么" |
| LCP（最大内容绘制时间） | 页面速度指标，首屏内容渲染耗时，< 1 秒为优秀 |
| MCP（模型上下文协议） | AI 助手调用外部工具的标准接口；做了它，Claude / Codex 能直接调用 gitflow 能力而非读技能文件 |
| dogfooding（吃自己的狗粮） | 用自己的产品开发自己的产品，既检验质量又是宣传案例 |

### 7.2 网站技术选型与页面结构

- **技术栈**：Astro 静态站点生成器 + GitHub Pages 托管（零运维成本、天然快、单人可维护）
- **语言**：中文主导；CLI 参考页保留英文命令原文（命令本身不可翻译）
- **核心页面**：首页（一句话定位 + 演示动图 + 安装命令）/ 文档 / 5 分钟快速上手 / 兼容性矩阵 / 更新日志 / FAQ / 对比页 / 案例页
- **GEO 地基文件**：`llms.txt`（摘要）+ `llms-full.txt`（全文）+ `sitemap.xml` + `robots.txt` + JSON-LD（SoftwareApplication / FAQPage / HowTo）

### 7.3 GEO 执行清单

1. 实体一致性：GitHub / crates.io / 官网 / 宣发文章的名称与一句话定位逐字统一。
2. `llms-full.txt` 覆盖：定位说明、完整命令参考、架构概述、兼容性矩阵、FAQ。
3. 问答式内容：FAQ 页直接回答"gf 和 gh 有什么区别""如何给 AI 编程加工程纪律"等长尾提问。
4. 月度 AI 引用抽检：在 Perplexity / ChatGPT / Kimi / 豆包中检索目标关键词，记录是否引用及引用准确性。

### 7.4 SEO 执行清单

1. 三端收录提交：Google Search Console、Bing 站长平台、百度资源平台。
2. 技术面：静态站点首屏 < 1 秒；语义化标题层级；内链网络；站点地图自动更新。
3. 关键词布局：核心词（Git 工作流 CLI、AI 编程工程化）+ 长尾词（gh glab 统一封装、GitCode PR 工具）。
4. 内容节奏：每月 2 篇系列文章同步掘金 / 知乎 / 微信公众号，官网为原文首发地（规范链接 canonical 指回官网，避免重复内容稀释权重）。

## 8. 风险与应对

| 风险 | 概率 | 应对 |
|------|------|------|
| 底层 CLI（尤其 gitcode v0.6.x）破坏性变更 | 高 | 契约测试 + 每周定时 e2e 预警；极端情况下 GitCode 降级为 beta 支持，不阻塞主线 |
| 单人产能瓶颈 / 维护者倦怠 | 中 | 每阶段只保留一条主线；范围裁剪优先于延期；dogfooding 提升 AI 协作效率 |
| GEO/SEO 见效慢（1–3 个月滞后） | 中 | 官网与 1.0 同步上线抢占时间窗；内容节奏（每月 2 篇）作为硬指标保障 |
| 1.0 后社区预期高于实际 | 低 | 兼容性矩阵与支持政策随 1.0 公开，管理预期 |
| 官网维护成本失控 | 低 | 静态站点 + 页面即文档（docs 目录直接渲染），不引入动态后端 |

## 11. 附：执行原则

1. **每阶段一条主线**：稳定化期不碰新功能，增长期不碰扩张项。
2. **测试驱动**：所有修复与新功能走红 → 绿 → 重构循环（项目既有规范）。
3. **月度发布**：每月固定发布窗口，路线图进度以发布版本为里程碑验收。
4. **dogfooding 优先**：路线图自身的执行继续使用 gf-workflow 四阶段编排——既是生产方式，也是案例素材。
