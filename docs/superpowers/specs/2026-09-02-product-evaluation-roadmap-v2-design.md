## 1. 背景与目标

上一版评估（2026-07-31，v0.9.0）诊断了四个结构性矛盾并规划了"稳定化 → 增长 → 扩张"三阶段路线图。5 周后，项目已推进到 v1.9.0（代码量从约 20.8K 行增长到约 41.7K 行），旧路线图中"稳定化阶段"（第 1–8 周）的多数任务已完成，"增长阶段"的基建任务也提前完成。

本文档回答两个问题：

1. **旧诊断哪些已兑现、哪些仍未解决、哪些是新出现的**——用五角色视角对当前真实仓库状态重新独立评估，而非复述旧结论。
2. **接下来怎么走**——项目目前处于三阶段路线图的哪个位置，下一步该做什么。

## 3. 多角色重新评估

### 3.1 产品负责人视角

| 维度 | 评估 |
|------|------|
| 强项 | 稳定化阶段退出标准已全部满足；官网与 GEO 基建比原计划（第 7–8 周骨架）走得更远、更完整；open issue 健康（无 P0/P1 积压） |
| 弱项 | bus factor=1 依旧未解，贡献者路径（#101）仍 open；`dev` 分支 CI 成功率长期停留 94%，多份报告反复标注却无整改动作——"观测疲劳"；文档报告持续膨胀，单人维护成本上升 |
| 机会 | `gf-workflow-batch`（#280）验证了批量编排能力，为对接 MCP 打基础；兼容性矩阵已结构化、机器可读，是现成的 GEO 内容素材 |
| 威胁 | 上游 CLI 漂移的 3 个 issue 挂在 priority:low，漂移速度可能快于修复投入；单人产能仍是增长/扩张两阶段最大制约 |
| 阶段判断 | **已越过稳定化，处于增长阶段收尾、向扩张阶段过渡**——增长阶段基建已完成但"运营"任务（贡献者、宣发）仍未收尾；扩张阶段两个旗舰项（MCP、效率报表）均未启动 |

### 3.2 架构师视角

| 维度 | 评估 |
|------|------|
| 强项 | 新增的 `cli-adapter-utils`（子进程调用去重）、`release-signer`（发布签名）是收敛式基础设施；契约测试 + 版本护栏（`prerequisites.rs`）+ 兼容性矩阵已把子进程耦合从"隐性负债"变成"显性受控边界"；core 已有 11 个细粒度 provider trait（`IssueProvider`/`PrProvider`/…），比"单一 Platform trait"更利于映射为 MCP 工具集 |
| 弱项 | e2e-gitlab、e2e-gitcode 仍不存在，三平台可信度不对等；`platform.rs` 命名（实际只是 URL 探测逻辑）与文档表述（"Platform trait"）不一致，易误导后续实现者（含 AI agent）；无定时 e2e 回归，契约测试防得住输出格式漂移、防不住 CLI 行为/退出码变化 |
| 机会 | MCP 服务器（#102）投入产出比最高——架构接缝已确认，可直接按 trait 一一映射为工具集，无需改动适配器代码 |
| 威胁 | `gh`/`glab` 破坏性变更仍直接传导；`gitcode` CLI 仍处于高波动版本区间 |
| 核心判断 | 子进程耦合风险**被控制住，未消除**——耦合本身没有减少，但已从失控变为受监控 |

### 3.3 DevOps / 可靠性视角

| 维度 | 评估 |
|------|------|
| 强项 | e2e-tests 已实化（不再空转）；`cargo deny check` / `cargo audit` 已并入 CI 强制门禁（非仅手动）；新增 `upstream-patrol.yml` 每日巡检上游 CLI 版本；发布模板未替换事故已加固（dry-run 强制扫描残留变量），近 5 个 tag 无异常 |
| 弱项 | 流水线增至 7 条，无统一健康看板；`gf pipeline report` 工具本身有统计口径 bug（in-progress run 误判为失败），已在 8 份报告中重复出现仍未修——"监控工具自身不可靠"；SBOM / `cargo vet` 仍是空白 |
| 机会 | 修复报告工具 bug 后即可信任现有报告体系做治理决策；`cargo-vet` 从提示语升级为强制门禁，补齐供应链可信度 |

| 核心判断 | DevOps 侧较 7 月底有实质性进步，三项旧弱项已工程化解决，剩余问题集中在"监控工具自身可信度"而非"缺失监控" |

## 4. 核心诊断：矛盾的演变

对照旧文档的四个结构性矛盾：

1. ✅ **"功能丰富 vs 可靠性不均"基本解决**——GitCode 崩塌已修复，三平台兼容性矩阵机器可读化，无 P0/P1 缺陷积压。
2. ⚠️ **"广度野心 vs 单人产能"依然是最大风险，且换了表现形式**——旧问题是"没有贡献者路径"，新问题是"有了路径却没人走上去"。
3. ⚠️ **"Agent 优先创新 vs 双层生态波动"被部分工程化**——契约测试 + 版本护栏已落地，但缺定时 e2e 回归，防得住格式漂移、防不住行为变化。
4. 🆕 **新增矛盾："观测在生成，但不转化为行动"**——五个角色中有两个（产品、DevOps）独立指出：CI 成功率连续多份报告停留同一水位无整改；`gf pipeline report` 统计 bug 复现 8 次仍未修。报告体系本身健康，但正在退化为"写了但没人看"的仪式，是本轮评估最一致的新发现。

## 5. 下一阶段路线图（增长收尾 → 扩张启动）

沿用旧文档"稳定化 → 增长 → 扩张"的战略排序，本路线图聚焦**收尾增长阶段的运营缺口**并**启动扩张阶段**。仍遵循"每阶段一条主线、单人产能下深度优于广度"的执行原则（见 [旧文档 §11](./2026-07-31-product-evaluation-roadmap-design.md#11-附执行原则)）。

### 5.1 P0：低成本高杠杆，立即处理

| 任务 | 细节 | 理由 |
|------|------|------|
| 修复 `gf pipeline report` 的 in-progress 误判 bug | 8 次复现同一统计缺陷 | 直接影响所有质量判断的可信度，属于低垂果实 |
| 实测复核 #90 正文里 GitCode `pr create/list/view` 问题 | 若未修复需重新开 issue 并标 `type:bug` | issue 关闭不代表问题解决，避免假象 |

### 5.2 P1：打破单人产能瓶颈（增长阶段收尾）

| 任务 | 细节 | 理由 |
|------|------|------|
| 标记 3–5 个 good-first-issue | 给 `CONTRIBUTING.md` 配上具体任务入口 | 基建已就绪，纯执行成本，是唯一能真正改变 bus factor=1 的动作 |
| 发布一篇 dogfooding 案例内容 | "如何用 gf 自己开发 gf"，放官网 blog 或掘金/知乎 | 现存最强但完全未被包装利用的传播素材 |
| 对 CI 成功率"Watch"档做根因归因 | 给 `gf-pipeline-analyzer` 加"连续 N 次同水位未处理即升级"机制 | 治理缺口而非技术缺口 |
| README 分列"纯 CLI 用户"与"Agent 编排用户"前置依赖 | 降低非 Agent 用户的认知负担 | `/gf-workflow` 路径仍是当前最大用户摩擦点 |

### 5.3 P2：启动扩张阶段

| 任务 | 细节 | 理由 |
|------|------|------|
| 启动 MCP 服务器（#102） | 新增 crate，按 core 的 11 个 provider trait 一一映射为工具集（`issue_*`/`pr_*`/`release_*`/…），复用现有接缝，不改动适配器代码 | 投入产出比最高的扩张项，Agent 生态窗口期不等人 |
| 补齐 e2e-gitlab、e2e-gitcode | 对齐 e2e-github 的覆盖深度 | 三平台可信度当前不对等，是最容易被用户踩中的空洞 |
| 契约测试接入定时 e2e 回归（cron，真实凭据） | 每周巡检，防住 CLI 行为/退出码变化 | 现有契约测试只防格式漂移 |

### 5.4 P3：维护性清理（不阻塞主线，见缝插针）

- 治理报告归档膨胀（pipeline-analysis-report 已近 10 份），按季度归档或加自动摘要。
- 移除 deprecated 的 `run` 子命令，保持命令面整洁。
- 澄清 `platform.rs` 命名与文档表述不一致，避免误导后续实现者。
- `cargo-vet` 从提示语升级为实际启用，补齐 SBOM 生成。

## 6. 风险与应对

| 风险 | 概率 | 应对 |
|------|------|------|
| good-first-issue 发布后仍无人认领 | 中 | 这是验证"内容飞轮是否生效"的直接信号，若 2 个月内无外部 PR，需重新评估贡献者路径策略而非继续加码 |
| MCP 服务器建在未闭环的契约测试上 | 中 | 先补 P0/P1 的报告可信度问题，再启动 MCP，避免在不可信的质量信号上做扩张决策 |
| 观测疲劳蔓延到新增的 MCP/e2e 指标 | 中 | P1 的"连续 N 次未处理即升级"机制需先落地，作为后续所有新增报告的治理模板 |
| 单人维护者倦怠 | 中 | 每阶段一条主线；P0/P1 任务量刻意控制在小范围，避免与 P2 扩张项并行消耗产能 |

## 8. 明确不做（延续旧文档判断）

以下方向本轮路线图仍**只预告、不实现**，与 2026-07-31 版一致：

- TUI（终端图形界面）交互模式
- 插件 / 扩展系统（第三方平台适配器与自定义命令）
- 新平台支持（Gitea / Forgejo / Bitbucket）
- Web 仪表盘
